## Findings that need a decision first

1. **Defaults.**
   - The publisher's current schemas now carry many of the text's defaults as `default` annotations, often conditional. These are the pinned `oas-3.1-schema-2026-11-05.json` and `oas-3.2-schema-2026-11-12.json`. They include:
     - `servers` = `[{"url":"/"}]`
     - Operation `deprecated` false
     - Parameter `required` false and `deprecated` false
     - Parameter `style` by location: path simple, header simple, query form, cookie form
     - Parameter `explode` by style, through `explode-for-form`; cookie true in 3.2
     - `allowReserved` false
     - `allowEmptyValue` false
     - Request Body `required` false
     - Header `required` and `deprecated` false, `style` simple, `explode` false
     - Encoding `style` form when `explode` or `allowReserved` is given
     - Security Scheme `deprecated` false (3.2)
     - `jsonSchemaDialect`
   - `rows/inventory.ts` never reads `default`, so none of these is a row.
   - Some defaults exist only in the text:
     - the XML `nodeType`, `attribute` and `wrapped` defaults (the base vocabulary carries none);
     - the Encoding `contentType` table;
     - "explode has no effect" for primitives and `deepObject`.
2. **The OAS dialect id differs between text and schema.**
   - Both texts, 4.24.1 [4.8.24.1], name `https://spec.openapis.org/oas/3.1/dialect/base` as "the OAS dialect schema id". Per 4.24.7 it MUST be the default when `jsonSchemaDialect` is absent.
   - The 2026 schemas default `jsonSchemaDialect` to `.../oas/3.1/dialect/2024-11-10` and `.../oas/3.2/dialect/2026-02-26`.
   - SPEC-FV-1 case 3 refuses a dialect "other than the OpenAPI dialect its publisher gives for the document's version line". By its own text, a 3.2 document whose schemas use `3.1/dialect/base` is using the 3.2 dialect. That case needs checking.
3. **Header `allowReserved` is ambiguous in 3.2.0.** 3.1.2 4.8.21 forbids it on headers. 3.2.0 4.21 drops it from the MUST NOT sentence but lists no such field. This is the spot where the README records a 2025-09-17 schema disagreement.
4. **Text-only validity rules missing from SPEC-FV-2.** I checked the 3.2 2026-11-12 schema's definitions for these and found none of them held:
   - each template expression at most once per path;
   - each server variable at most once per URL;
   - a server variable's `default` is in its `enum`;
   - `querystring` appears at most once and never alongside `query`;
   - a tag's `parent` exists and has no cycles;
   - `defaultMapping` is required when the discriminating property is optional.
5. **SPEC-FV-2's section numbers are correct.** I checked its 3.1.2 and 3.2.0 section numbers against both texts.

## Strings whose grammar a specification defines

**A. Grammars the OAS text cites**

- **`openapi` version:** major.minor.patch (2.1 [4.1]). The pattern itself comes from the publisher's schema.
- **URI, URI reference and relative reference:** RFC 3986 §4.1 and §4.2, resolved by §5.1.1–5.1.4. Used by:
  - `$self`, `$ref` (Reference Object and Path Item), `jsonSchemaDialect`, `$schema`, `$id`, `$dynamicRef`;
  - `termsOfService`, `contact.url`, `license.url`, `externalDocs.url`;
  - `operationRef`, `externalValue`, `openIdConnectUrl`, `oauth2MetadataUrl`;
  - `discriminator.mapping` and `defaultMapping` values (a component name or a URI reference, with the `./` rule);
  - Security Requirement keys in 3.2 (a component name or a URI).
- **API URLs:** server `url` and the OAuth URLs, per RFC 3986 (4.5.2, 4.12.4).
- **Server URL template:** the 3.2 §4.6 ABNF, using RFC 6570 literals/pct-encoded/ucschar/iprivate with Errata 6937. 3.1.2 has only "{braces}".
- **Path template:** the 3.2 §4.8.2 ABNF, using RFC 3986 pchar and §3.3. 3.1.2 has prose only (§3.5).
- **JSON Pointer in a fragment:** RFC 6901, with `~0`/`~1` and percent-encoding in a URI (4.1.2.2.2, 4.20.2.1).
- **Runtime expression:** the §4.20.3 ABNF.
  - `json-pointer` from RFC 6901.
  - `char` from RFC 8259 §7 (3.1.2: RFC 7159).
  - `token` from RFC 9110 §5.6.2 (3.1.2: RFC 7230 §3.2.6).
  - Also the `{expr}` form embedded in strings: callback keys, link values.
- **Link `parameters` key:** `[location.]name`, in §4.20.1 prose.
- **Media type:** RFC 6838 (4.14.2 [3.6]).
- **Media type range:** 3.1.2 cites RFC 7231 Appendix D (4.8.13.1, 4.8.17.1); 3.2.0 names ranges and cites nothing.
- **Encoding `contentType`:** a comma-separated list of media types or wildcard media types (4.15.1.1).
- **Status code key and range:** `1XX`–`5XX`, uppercase X (4.16.2); codes from the IANA HTTP Status Code registry.
- **Header names:** RFC 9110 §5.1, case-insensitive (3.1.2: RFC 7230 §3.2). The 2026-11-12 schema also applies a `token` pattern to header parameter names.
- **Component keys and Link names:** `^[a-zA-Z0-9\.\-_]+$` (4.7.1, 4.17.1).
- **Extension names:** `^x-`, with `x-oai-` and `x-oas-` reserved (5).
- **HTTP auth scheme:** RFC 9110 §16.4.1 and §11.1 plus the IANA registry (3.1.2: RFC 7235).
- **License `identifier`:** an SPDX license expression.
- **`description`:** CommonMark 0.27 at minimum.
- **XML namespace:** a non-relative IRI under RFC 3987 (3.1.2: URI), matching Namespaces in XML 1.1 (4.26.4).
- **Percent-encoding:** RFC 3986; form-urlencoded per WHATWG URL (3.1.2: RFC 1866).
- **Style output:** RFC 6570; `style: cookie` follows RFC 6265.
- **Sequential and other media types:** RFC 7464 and 8091, text/event-stream per [HTML], RFC 2046/7578 (multipart), RFC 9264 (linkset), RFC 4648 (base64).
- **`format` values and `pattern`:** JSON Schema Validation §7.3 and ECMA-262. These are already in the hand list.
- **QUERY method:** draft-ietf-httpbis-safe-method-w-body-08.

**B. Named by the text without a cited grammar (my attribution, not checked)**

- Contact `email` ("form of an email address"): probably RFC 5321/5322.
- The 3.2.0 media type range: probably RFC 9110 media-range.
- `additionalOperations` keys: probably RFC 9110 method token.
- Cookie parameter names: RFC 6265 cookie-name.
- XML `name` and `prefix`: XML Name / NCName.
- OAuth scope names: RFC 6749 scope-token.
- No grammar at all: `info.version`, webhook, callback, example and tag names, `bearerFormat`.

## Pure validity rules left out

- **Already in SPEC-FV-2:** `operationId` uniqueness; template↔parameter correspondence; duplicate templated hierarchies; duplicate (name, in) parameters; tag-name uniqueness; `additionalOperations` collisions.
- **Not held by the pinned 3.2 schema (2026-11-12) as far as I checked, and not in FV-2:**
  - each template expression at most once (3.2 4.8.2);
  - each server variable at most once (3.2 4.6);
  - a server variable `default` is in its `enum` (4.6.1);
  - `querystring` appears at most once and never with `query` (3.2 4.12.1);
  - a tag's `parent` exists and is acyclic (3.2 4.22.1);
  - `defaultMapping` is required when the discriminating property is optional (3.2 4.25.1).
- **Not in FV-2; I did not check the schemas:**
  - Discriminator only beside `oneOf`/`anyOf`/`allOf`, with alternatives listed explicitly (4.25.2).
  - Link `operationId` must exist and be unique; `operationRef` must point to an Operation (4.20.1).
  - Security Requirement keys must name a declared scheme (4.30).
  - Server `url` has no query or fragment (4.5.1).
  - XML `name` is required where it cannot be inferred (3.2 4.26.3).
  - Style/type combinations such as `deepObject` with objects only (4.12.3).
  - 3.1.2 only: encoding keys must be properties (4.8.14.1); multipart requires a schema (4.8.15.3).
  - Patterned field names are unique (3).
  - YAML constraints: RFC 9512 §3.4 (3.2); JSON-schema tags and scalar keys (3.1.2 4.2).
  - Request Body `content` SHOULD have at least one entry.
- **Held by the 2026-11-12 schema:**
  - Parameter `schema` xor `content`.
  - `querystring` requires `content`.
  - Path `required` is true, and the path name pattern.
  - Style enums per location.
  - License `identifier` xor `url`.
  - Example field exclusions.
  - `encoding` versus `prefixEncoding`/`itemEncoding`.
  - Link `operationRef` xor `operationId`.
  - Responses has at least one entry.
  - Component key pattern.
